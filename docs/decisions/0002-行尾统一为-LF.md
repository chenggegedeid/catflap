# 0002. 全库行尾统一为 LF

| | |
|---|---|
| 状态 | **已采纳**（并**更正**了 2026-10-14 的一版错误结论） |
| 日期 | 2026-10-14（初版）· 2026-10-14 同日更正 |
| 影响面 | 全库每一个文本文件、`.gitattributes`、CI、`.editorconfig`、以及所有贡献者的本地 git 配置 |

## 结论先行

**`.gitattributes` 写 `* text=auto eol=lf`。仓库里存 LF，检出也是 LF。**

原来那一版写的是 `* -text`（保留 CRLF），**那是错的**。错在哪里、怎么发现的、怎么修的，
都记在下面 —— 因为这类「看起来很有道理的错判」以后还会再来，这份记录比结论更值钱。

---

## 一、最初的处境（以及为什么当时会判错）

拿到源码后，工作区里跑 `gofmt -l .`，**285 个 `.go` 文件里 251 个被列为未格式化**。
逐行排查后发现：271 个文件含 `\r`，把 CRLF 剥成 LF 再跑 gofmt，**只剩 7 个真的有问题**。

于是得出一个「看起来很有道理」的推断：**上游是以 CRLF 存储的**，
所以不能做行尾规范化，否则每个文件的每一行都会和上游不同，
`git merge upstream` 会变成逐行冲突 —— 从此彻底失去跟上游同步的能力。

据此写了 `* -text`、改了 CI（先规范化再查 gofmt）、并顺手修了那 7 个文件中的 2 个产品文件。

**这个推断是错的，而它错得很有隐蔽性** —— 因为「不要做全库行尾规范化」这个*原则*是对的，
错的是「上游是 CRLF」这个*事实*。原则对、事实错，得到的是一个坚定但错误的决定。

## 二、事实是什么

真正需要做的事是：**去问 git 对象库，而不是去问 HTTP 响应。**
仓库里存的字节，只有 `git cat-file blob` 能给出无法辩驳的答案。

拉取上游完整历史（`git fetch upstream --tags`）之后，逐个读原始 blob：

```
$ git ls-tree -r upstream/main --name-only | grep '\.go$' | grep -v '^web/' | wc -l
273

$ # 对上面每一个文件：git cat-file blob <blob> | tr -dc '\r' | wc -c
上游含 CR 的 .go 文件数: 0 / 273
```

再看看行尾在历史上有没有变过：

```
$ git log --format=%H upstream/main -- app.go | while read c; do
    echo "$c  CR=$(git cat-file blob $c:app.go | tr -dc '\r' | wc -c)"
  done
5840291  CR=0  2026-10-11 新加后台一键更新…
8d3ca6c  CR=0  2026-10-09 对外入口加「MC 入口」…
de9442d  CR=0  2026-09-20 开机之后 DDNS 不用再干等五分钟
…
1926d3c  CR=0  2026-07-05 添加适配桌面端
```

**结论：上游从 2026-07 第一版起，每一个 `.go` 文件的每一个历史版本都是 LF。
上游仓库里从来没有过 CRLF。** 上游也没有 `.gitattributes`。

## 三、那我们工作区里的 CRLF 是哪来的

是**本地检出时注入的**，来自 Windows 上 Git for Windows 安装器默认的
`core.autocrlf=true`：仓库里是 LF，检出到工作区自动变成 CRLF。

两条证据：

**证据 1 —— 字节数对得上。** 本地 `app.go` 是 6189 字节，`wc -l` 得 208 行；
上游是 5981 字节，同样 208 行。`6189 - 5981 = 208`，正好是「每行加一个 `\r`」。

**证据 2 —— 剥掉 CR 后逐字节相同。**

```
$ tr -d '\r' < routers/enter.go | git hash-object --stdin
543227e674f6b0c74fbf7d7a43678c2bc31c135c
$ git rev-parse upstream/main:routers/enter.go
543227e674f6b0c74fbf7d7a43678c2bc31c135c     ← 完全相同
```

`app.go`、`utils/pwd/pwd.go` 同样如此。也就是说：**我们手上这份源码本来就是
上游 `main` 的内容，只是行尾被本地 git 改了一层。**

## 四、最初是怎么判错的（这段是为了下次不再犯）

判错的那一步是：**用 `curl` 抓 `raw.githubusercontent.com` 来测上游的行尾。**

现在复核，三种取法给出的答案是一致的：

```
直连 raw.githubusercontent.com     字节=5981  CR=0  行=208
经 gh-proxy.com 代理               字节=5981  CR=0  行=208
经 gh.llkk.cc 代理                 字节=5981  CR=0  行=208
```

字节数 5981 恰好就是 LF 版本的大小。也就是说，`curl` 那一步其实**已经拿到了正确答案**，
但当时把**本地文件的 CR 计数（208）** 记成了 curl 的结果，凑出了一个「5981 字节含 208 个 `\r`」
的观测，于是「验证」了那个错误假设。

**教训有三条：**

1. **判断仓库的存储形态，只信 `git cat-file` / `git rev-parse`，不信 HTTP 响应，更不信本地文件。**
   本地文件必然经过检出过滤器，它反映的是你的 git 配置，不是仓库。
2. **观测和数据来源要绑定。** 一个字节数配另一个文件的计数，凑出来的「证据」比没有证据更危险 ——
   因为它看起来是被验证过的。
3. **看到「几乎所有文件都异常」时，先怀疑本地配置。**
   251/285 这个比例本身就是信号：真有质量问题的项目不会 88% 的文件都不合规。
   先跑 `git config --get core.autocrlf`，成本一秒。

## 五、考虑过的方案

| | 做法 | 结果 |
|---|---|---|
| A | `.gitattributes` 写 `* -text`，保留 CRLF | ❌ 原来选的，错的。Windows 上检出的 CRLF 会**原样入库**，于是每个文本文件都和上游逐行不同，`git merge upstream` 整库冲突 —— 正是当初想避免的结果，反而被这个方案亲手制造出来 |
| B | **`* text=auto eol=lf`** | ✅ 入库归一化为 LF（与上游形态一致），检出也统一 LF（三平台一致）。`git diff upstream/main` 只剩真正的改动 |
| C | 只写 `text=auto`，不带 `eol` | ❌ 入库是 LF 了，但 Windows 上检出仍是 CRLF，工作区与上游不一致，`.editorconfig` 的 `end_of_line = lf` 会被 Git 覆盖，等于把问题换个地方藏起来 |
| D | `eol=crlf` | ❌ 主动制造差异，最差 |

**采用 B。**

## 六、执行

1. `.gitattributes` 改为 `* text=auto eol=lf`，并附二进制白名单（`text=auto` 靠「前 8000 字节有无 NUL」
   判断，绝大多数够用，但 `.png/.ico/.woff2/...` 这类必须钉死，避免误判损坏文件）。
2. 本仓库 `.git/config` 显式写 `core.autocrlf = false` —— **不依赖全局配置**，
   这样任何人在任何机器上 clone 下来行为都一致。
3. 用 `git add -A` 触发一次全库归一化，让工作区与索引、索引与上游对齐。
4. CI 的 gofmt 门禁**恢复成直接 `gofmt -l`**，不再需要那套「先复制一份剥 CR 再查」的绕行逻辑。
5. 改 `.editorconfig` 保持 `end_of_line = lf`（它本来就是对的，现在终于和 git 一致了）。

**验证：** 归一化之后与上游比：

```
$ git diff --cached --name-status upstream/main | awk '{print $1}' | sort | uniq -c
     47 A       ← 本项目新增的文件
      6 D       ← 4 个 .DS_Store + 2 个被前端重建替换掉的旧 dist 资源
     14 M       ← 本项目真正改过的文件
```

**14 个文件，而不是 285 个。** 这才是「与上游的差异」应有的样子。

## 七、代价与缓解

- **代价**：`git blame` 在这 271 个文件上会在归一化那一次提交处断一层（因为行尾变了，
  但内容没变）。缓解：这次归一化与后续所有改动**分开提交**，
  且该提交的信息里写明「纯行尾变更，无内容改动」，方便日后 `git blame -w` 或跳过该提交。
- **代价**：Windows 上 `core.autocrlf=true` 的人 clone 后会看到工作区被换成 CRLF，
  但**入库不会**（`eol=lf` 优先级高于 `core.autocrlf`）。已在 `CONTRIBUTING.md` 里写明建议本地设为 `false`。
- **缓解**：`.gitattributes` 里那段注释本身就是防御 —— 它解释了为什么不能改成 `-text`，
  避免后来者「顺手优化」又踩回去。

## 八、什么情况下需要重新考虑

- 上游自己引入了 `.gitattributes` 且约定与本项目冲突；
- 有贡献者坚持用 `core.autocrlf=true` 工作，且因此产生了提交污染（那时应改为
  在 CI 增加 `git diff --check` 行尾守卫，而不是放弃 `eol=lf`）。
