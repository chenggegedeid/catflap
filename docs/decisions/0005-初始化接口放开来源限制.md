# 0005. 初始化接口 `POST /api/auth/setup` 放开来源限制

- 状态：已采纳
- 日期：2026-10-15
- 影响面：`routers/auth_routers.go`、`api/auth_api/setup.go`、README/文档
- 取代：v1.0.0 引入的「初始化仅限本机」策略

## 处境

v1.0.0 把 `POST /api/auth/setup` 限制为只能从回环地址发起
（`middleware.LoopbackOnly`，依据 TCP 对端地址而非可伪造的代理头）。

要防的是这件事：**在「装好但还没初始化」这个窗口里，任何能打开页面的人都能
抢先设置管理员密码**。而改密码需要旧密码 —— 也就是说这台机器会被接管，且
原主人拿不回来：这台机器上的 DDNS 凭据、反向代理配置、证书一并归了对方。

代价则是：**初始化必须跑到机器跟前，在它本机上开浏览器**。对无头设备、
远程装机、容器化部署都很别扭 —— 这正是本次改动的触发点。

## 决定

**去掉来源限制**，`/api/auth/setup` 对任何来源开放（仍然只在未初始化时可用，
逻辑不变）。

## 理由

1. 这是自建服务的常规形态。同类产品（NAS 套件、路由器固件、其它自托管面板）
   普遍是「装完打开页面，第一步设密码」，并没有强制本机。
2. 窗口期是**用户自己控制的**：装完立刻初始化，窗口就只有几分钟；真正长期
   暴露的是「装完忘了初始化」，而那种情况下本机限制也不解决问题（用户压根
   没打开过页面）。
3. 本机限制带来的摩擦是**确定会发生的**，而它防住的攻击是**需要有人正好在
   同网段且正好在这个窗口内动手**的。用户明确表示局域网里没有这种威胁。

## 代价与风险（务必知悉）

- **同网段内可被接管**：未初始化期间，谁先打开页面谁就能设密码。这不是
  「抢注」，是接管 —— 且不可逆。
- 若这台机器**直接暴露在公网**（端口转发 / 云主机），风险显著放大：任何
  扫到这个端口的人都能接管。**这种情况必须装完立即初始化**，或在前置反代
  上加一层认证。

## 缓解措施（保留的能力）

- `middleware.LoopbackOnly` / `IsLoopbackRequest` / `isLoopbackAddr`
  **保留不删**，测试也保留。将来若要恢复本机限制、或做白名单 / 只允许本机
  调用的管理接口，直接复用；那套「从 TCP 对端地址判断、不信代理头」的写法
  是解决过伪造 `X-Forwarded-For` 问题的成果，不要重新发明。
- `/api/auth/setup` 仍然只在未初始化时生效，初始化之后它不会成为改密码的
  后门（改密码走需要鉴权的 `PUT /api/auth/password`）。

## 如何回退

在 `routers/auth_routers.go` 的 `auth/setup` 路由上把
`middleware.LoopbackOnly` 中间件加回去即可（一行）。中间件与测试都还在，
不需要恢复别的代码。
