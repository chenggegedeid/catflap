# 架构决策记录（ADR）

这里保存**已经定下来的、会影响后续所有工作的**技术决策。每条记录写清楚：
当时的处境、考虑过哪些方案、为什么选了这个、以及代价是什么。

**目的不是留档，是防止后人（包括三个月后的自己）把已经论证过的事情再推翻一次。**
如果你觉得某条决策错了，请新开一条 ADR 说明理由并标注「取代 ADR-XXXX」，
而不是直接把旧的那条改掉 —— 决策变更的过程本身就是重要信息。

## 什么时候该写一条

- 改变全库约定（命名、行尾、目录、错误处理风格）
- 引入或放弃一个依赖 / 框架
- 影响「与上游同步成本」的任何决定
- 安全相关的取舍（哪些限制做在代码里、哪些写进文档靠用户）
- 明确决定**不做**某件事（例如「不用 Go 的 plugin 包」），并且这件事以后一定会有人再提

不需要写 ADR 的：局部实现细节、可以随时改回来的事情。

## 模板

```markdown
# NNNN. 标题（陈述句，例如「保留 xxx」而不是「关于 xxx 的讨论」）

- 状态：已采纳 / 已取代（被 NNNN 取代） / 已废弃
- 日期：YYYY-MM-DD
- 影响面：全库 / 某个模块 / 仅构建流程

## 处境

当时面对什么问题？有哪些硬约束（上游现状、许可、平台、用户预期）？

## 考虑过的方案

1. 方案 A —— 优点 / 缺点
2. 方案 B —— 优点 / 缺点

## 决定

选了哪个。为什么。

## 代价与缓解

这个决定要付出的代价是什么？怎么减轻？

## 什么情况下应该重新考虑

写清楚触发条件，避免以后凭感觉推翻。
```
