# 0001. 保留 Go module 名 `linkstar`

- 状态：**已废止（2026-10-14 晚）** —— 被 [0004](0004-改用自有-go-module-名.md) 取代。
  废止原因：本 ADR 的第 3 条理由（保留与上游 `git merge` 的能力）在方向调整后
  不再成立。**本文保留原文，是为了让「为什么当初这么定、后来为什么推翻」可读。**
  请不要照本文执行。
- 日期：2026-10-14
- 影响面：全库

## 处境

本项目是 `ZluxYao/LinkStar` 的衍生项目，品牌已更名为 **Catflap**。按常理，`go.mod`
第一行也应该跟着改：

```
module linkstar   →   module catflap
```

但代码库里有两件事和这个名字绑死了：

1. **168 个文件**写着 `import "linkstar/..."`（`grep -rl '"linkstar/' --include=*.go` 的实测值，
   总文件数 274 个，另有 183 个文件在注释里提到过这个名字）；
2. `modules/update/update.go:521` 的 `checkBinary()` 用 Go 的构建信息做校验：

```go
info, err := buildinfo.ReadFile(path)
if err != nil || info.Path != "linkstar" {
    return errors.New("这不是 …程序，请上传 Release 里下载的文件")
}
```

`buildinfo.Path` 就是 **module 路径**。也就是说：module 名一改，一键更新会**拒绝所有合法二进制**，
而这个错误只会在用户点更新的那一刻才暴露 —— 上传的文件被判定为「不是本程序」。

第三条约束是隐性的但更重要：本项目长期要保持从上游合并的能力（见 §上游同步策略）。

## 考虑过的方案

### 方案 A：改名为 `catflap`，同步改 168 处 import + `checkBinary` 的校验值

- ✅ `go.mod` 与项目名一致，观感正确
- ❌ 要动 183 个文件，其中绝大多数改动是纯噪音（用户在界面上看不到任何区别）
- ❌ `git merge upstream/main` 时，**每一个被上游改过的文件都会冲突**（因为每一行的
  import 都不同），等于主动放弃上游同步
- ❌ 任何一次漏改都会编译失败或运行期 panic，而收益是零

### 方案 B：保留 `linkstar`，只改用户可见的东西

- ✅ `checkBinary()` 一行都不用动，更新校验继续有效
- ✅ 上游合并的冲突面收敛到「我们真正改过的文件」
- ✅ 零风险、零返工
- ❌ `go.mod` 第一行与项目名不一致，看起来奇怪

## 决定

**采用方案 B：保留 `module linkstar`。**

三条理由按权重排序：

1. **收益为零，风险非零。** 这个 module 名不对外提供库、不会被用户看到、不影响任何功能。
   唯一"收益"是观感。
2. **它是 `checkBinary()` 的校验基准。** 改它就得同步改校验值，而校验一旦失效，
   后果是用户的更新功能静默坏掉。
3. **它决定这个分支能活多久。** 品牌可以改、界面可以改、图标可以换，这些都不影响与上游
   的合并；但重命名 module 会让每次同步都变成全库冲突，最后只能放弃同步、变成一条死分支。

也就是说，这不是"懒得改"，而是**用一行代码的观感换取长期的同步能力**。

## 代价与缓解

- **代价**：`go.mod` 与项目名不一致，新人会疑惑。
- **缓解**：
  - `go.mod` 里加注释说明原因（指向本文件）；
  - `CONTRIBUTING.md` 的「上游同步策略」一节明确写「`linkstar` 这个名字不要动」，
    并列进 PR 自查清单；
  - 二进制名、Release 资产名、界面文案、后台路径、证书主题**全部**改成 Catflap ——
    用户能感知到的地方一个不留。

## 什么情况下应该重新考虑

- 决定**永久停止**从上游合并（例如上游停更两年，或功能路线已完全分化）
- 需要把某些包作为独立 library 对外发布（那时 module 路径会成为公共 API 的一部分）
- Go 工具链未来提供安全的 module 重命名机制，且能迁移 `buildinfo.Path` 的历史值

以上任意一条成立时，重开一条 ADR 讨论，不要直接改。
