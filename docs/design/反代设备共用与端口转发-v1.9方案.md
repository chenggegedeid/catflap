## 二、设备表怎么共用（关键设计）

### 不能这么干

让 proxy 直接读 `stun.Runtime.Config.Devices` —— 会造成 **proxy 依赖 stun**，
而 stun 启动时要跑几秒网络探测（探测公网 IP、选最快的 STUN 服务器），
反代的监听不该等它。这条原则前面几版已经坚持过几次，不能破。

### 正确做法：设备下沉成公共模块

```
        ┌──────────┐        ┌──────────┐
        │   stun   │        │  proxy   │
        └────┬─────┘        └────┬─────┘
             │                   │
             └─────────┬─────────┘
                       ▼
                ┌─────────────┐
                │   device    │   ← 新模块，设备只存一份
                │ config/devices.json
                └─────────────┘
```

- 新建 `modules/device`，设备存 `config/devices.json`
- stun 和 proxy 都引用它，**两边互不依赖**
- 依赖方向是「业务模块 → 公共模块」，和现在 `core/lanscan`（扫描）、
  `core`（监听端口）的做法一致

### 迁移

启动时一次性：

1. 若 `config/devices.json` 不存在，但 `config/stunConfig.json` 里有 `devices`
   → 搬过去，stunConfig 里的 `devices` 字段留空（不再写）
2. 若两边都有 → 以 devices.json 为准，不合并（避免重复）
3. 老配置的设备 ID 保持不变（穿透服务引用的是 ID，不能变）

**幂等**：只在 devices.json 不存在时搬。最坏情况是不搬，穿透照样能用。

### 谁要跟着改

引用设备的地方：`modules/stun/{lookup,scheduler,redirect,mc_entry}.go`、
`modules/home/hydrate.go`、`api/stun_api/*`。都是改 import 路径和调用点，
逻辑不用动。

**风险**：中等 —— 动的是穿透的设备存储，要实测"老配置升级后设备和服务都在"。

## 三、站点怎么挂设备 —— 用 IP 自动推导，不存冗余字段

### 关键：设备本来就是按 IP 存在的

`Device{ id, name, ip }` 里，**IP 就是设备的标识**。那站点的归属
根本不需要再存一个 `deviceId` —— 从 backend 的 host 一算就出来了：

```
站点 backend = "192.168.1.20:5000"
                 └────┬────┘
              设备表里 IP 匹配 → 群晖 NAS
```

**不存 deviceId 的三个好处**：

1. **单一数据源**：改了 backend 的 IP，归属自动跟着变，不会出现
   "站点写着属于 A 设备、IP 却是 B 的"这种不一致
2. **老配置零迁移**：现有站点本来就只有 backend，打开就自动归组，
   不用跑任何搬运代码
3. **少一个字段要维护**：设备改名、改 IP 都不用去同步站点表

### 流程上仍然是"先有设备，才能加服务"

你要的顺序照样成立，只是"挂"这个动作变成自动的：

```
1. 加设备：填 IP + 起个名字（群晖 NAS / 192.168.1.20）
2. 加服务：选设备 → IP 自动填好 → 只填端口和域名
3. 归属：IP 一匹配就归到那台设备下，不用手动挂
```

没设备时反代页给一个引导（"先加一台设备"），加不了服务。

### 保存时的校验

backend 的 host 在设备表里**找不到**时直接拒，并说清楚怎么补：

> `192.168.1.20` 还不是设备，先在设备列表里把它加进来

这样"必须挂设备"是**硬保证**，但不是靠存字段，而是靠匹配。

### 一个例外：backend 填了域名

现在 backend 允许填域名（`example.com:8080`），这种情况**匹配不到 IP**。
处理：允许手动指定一台设备（存一个可选的 `deviceId` 覆盖自动推导）。

- 大多数情况（填 IP）：`deviceId` 为空，自动归组
- 少数情况（填域名）：手动选一台，否则拒

**不主动解析域名去匹配 IP** —— 域名可能解析到多个地址，
也可能随时变，推出来的归属不可靠，不如让用户明确选一次。

### 端口转发同理

转发目标也是 `IP:端口`，用同样的 IP 匹配。所以上面这套逻辑
站点和端口转发**共用一份**，不用写两遍。

## 四、端口转发独立成一个功能

### 为什么分出来

现在端口转发是"站点留空域名 + 填独占端口"，混在站点里，
导致站点这个概念要同时表达两件事：

- **站点**：域名 → 内网服务（按域名分流）
- **端口转发**：端口 → 端口（不看域名）

分开之后各自清晰，也和 lucky / 爱快一致。

### 新结构

```
config/proxy.json
├── entry      { httpPorts[], httpsPorts[], certId }
├── devices    （引用公共设备表）
├── sites[]    站点：deviceId + 域名 + 后端端口 + 协议
└── forwards[] 端口转发：listenPort + target + protocol + enabled
```

**端口转发一条**：

```json
{ "id": 1, "listenPort": 8081, "target": "192.168.1.20:80",
  "protocol": "tcp", "enabled": true, "description": "给外面的监控用" }
```

- 站点表里**去掉 ListenPort**（不再有"独占端口"这回事）
- 端口转发就是纯端口映射，和域名无关
- 界面上独立一个「端口转发」区块，和站点列表平级

## 五、入口多端口 + 服务只选协议

（这条上一版已确认，合并进来）

- 入口：`httpPorts[]` / `httpsPorts[]`，可以配多个
  （内网走 80、外网映射走 8080，同一批站点两个端口都能访问）
- 服务：不填端口，只选 **HTTP / HTTPS / 自动**
- 入口配了证书时**默认 HTTPS**
- 要新端口就在入口加，不用每个服务填一遍

## 六、健康检查频率：1 小时太慢，性能完全不是问题

你担心占用 CPU 和内存，先给数字（按 20 个服务算）：

| 频率 | 每小时探测次数 | 开销 |
|---|---|---|
| 1 小时 1 次 | 20 次 | 无感 |
| **5 分钟 1 次** | 240 次 | 仍然无感 |
| 1 分钟 1 次 | 1200 次 | 内网依然无感 |

一次探测就是**一次 TCP connect 然后立刻关掉**：

- 后端可达（内网）：不到 1 毫秒
- 后端不可达：等超时，建议超时设 1 秒
- 内存：每条服务几十字节的状态（上次结果、连续失败次数）

CPU 占用可以忽略；240 次/小时摊到每秒是 **0.07 次**。
真正占资源的只有"全部超时"的极端情况，而那也只是几个 goroutine 等 1 秒。

**所以瓶颈不是性能，是发现故障的速度：**

- 1 小时：服务挂了最长 1 小时才知道，健康检查基本白做
- **5 分钟**：推荐。多数故障能在几分钟内发现，开销可忽略

建议：**默认 5 分钟，可在设置里改**（给 1/5/15/60 分钟几档）。
只探 TCP 连通性，不探 HTTP —— 避免给内网服务造成负担，
也避免某些服务把健康检查请求当成攻击。

## 八、分步实施（v1.9）

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 设备下沉公共模块 + 迁移（最要小心） | **中高** |
| 2 | 站点按 IP 自动归属（不存 deviceId）+ 保存时校验 | **低**（零迁移） |
| 3 | 入口多端口（httpPorts/httpsPorts） | 低 |
| 4 | 端口转发独立成 forwards（同样按 IP 归属） | 中（要拆现有配置） |
| 5 | 服务表单改成选协议（有证书默认 HTTPS） | 低 |
| 6 | 界面：设备列表 → 服务列表 + 端口转发区块 | 中 |

第 2 步因为改成"按 IP 自动推导"，**不用写迁移代码** —— 老配置的站点
本来就带 backend，打开自动归组。这是这轮最大的简化。

剩下要写迁移测试的只有第 1 步（设备搬到 devices.json）和第 4 步
（把"站点独占端口"拆成端口转发）。
