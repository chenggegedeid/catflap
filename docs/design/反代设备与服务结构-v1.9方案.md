# v1.9 方案：反向代理改成「设备 → 服务」两层结构

状态：待确认 · 2026-10-15
触发：用户提出反代界面太乱，应像穿透那样按设备分组，且流量统计要显示服务名

---

## 一、想解决什么

反代现在是**一张扁平的站点表**：

```
nas.example.com  → 192.168.1.20:5000
web.example.com  → 192.168.1.20:8080
git.example.com  → 192.168.1.31:3000
```

问题有三个：

1. **看不出哪几个站点在同一台机器上** —— 上面前两条其实是同一台 NAS，
   但界面上并列三条，毫无关联感
2. **机器没有名字** —— 只看到 `192.168.1.20`，不知道那是"群晖"还是"飞牛"
3. **流量统计只显示编号** —— 显示"站点 #3""穿透 #1-2"，不知道是谁在跑流量

穿透那边是「设备 → 服务」两层，清晰得多。反代照做一遍，两边就一致了。

---

## 二、关键洞察：数据本来就是对齐的

不需要重新设计模型 —— 反代站点里的 `backend` 字段天然就是两层：

```
backend = "192.168.1.20:5000"
           └────┬────┘ └─┬─┘
           穿透的 Device.IP  穿透的 Service.InternalPort
```

| 穿透 | 反代 | 来源 |
|---|---|---|
| Device.IP | `192.168.1.20` | backend 的 host 部分 |
| Service.InternalPort | `5000` | backend 的 port 部分 |
| Service.Name | 站点名 | 新增（见下） |

所以这次改动的本质是：**把已经存在的信息显式化成"设备"这一层**，
而不是发明新概念。

---

## 三、设计

### 3.1 数据模型

**新增反代设备**（存在 `config/proxy.json` 里，与穿透的设备表分开）：

```json
{
  "devices": [
    { "id": 1, "name": "群晖 NAS", "ip": "192.168.1.20", "description": "书房那台" }
  ]
}
```

**站点加两个字段**：

```go
type Site struct {
    ...
    DeviceID uint   `json:"deviceId"`  // 属于哪台设备；0 = 还没归组
    Name     string `json:"name"`      // 服务名，如「照片库」
}
```

- `Name` 留空时**回落到第一个域名**（`nas.example.com`），老配置不用改就有名字
- `DeviceID` 为 0 时按 backend 的 host 自动推断（见迁移）

**为什么设备表不共用穿透的**：反代不能依赖 stun（那个模块初始化要跑几秒
网络探测，反代的监听不该等它 —— 这条原则前面几版已经坚持过几次了）。
两边各存各的，需要时在 api 层聚合，和"域名从 DDNS 选"是同一个做法。

### 3.2 迁移（最关键的一段）

**老配置必须自动变成新结构，不能让用户手动整理。**

读配置时做一次：

```
对每个 DeviceID == 0 的站点：
  1. 解析 backend 拿到 host（如 "192.168.1.20"）
  2. 设备表里找有没有这个 IP
     - 有 → 站点挂上去
     - 没有 → 新建一台设备，名字默认用 IP（用户之后可改）
  3. 写回 DeviceID
```

结果：升级完打开反代页，原来的三条站点**自动收成两台设备**，
名字先显示为 IP，用户点一下改成"群晖 NAS"就行。

`127.0.0.1` / `localhost` 这类归到一台叫「本机」的设备 ——
跑在 Catflap 自己机器上的服务是常见情况，单独归一组比散着强。

### 3.3 界面

**反代页**改成和穿透页同样的结构：

- 上面：入口配置（不变）
- 中间：**设备列表**（卡片，和穿透的设备卡片同一套样式）
  - 设备头：状态点 + 名字 + IP + 「N 个服务」+ 加服务/编辑/删除
  - 设备里：该设备的站点列表（就是现在的服务卡片，去掉后端 IP 那一列，
    因为已经在设备头上了）
- 「添加站点」改成两步：先在哪台设备 → 再填域名和端口
  - 选设备时可以用**已有的扫描选机器**（v1.7 做的那个），选了自动建/复用设备

**服务卡片**上显示：服务名（照片库）+ 域名 + 端口，不再重复 IP。

### 3.4 流量统计显示服务名

现在返回的是 `bySite{"3": ...}` / `byTunnel{"s1-2": ...}`，前端只能显示编号。

**改后端返回名字映射**（api 层把 ID 解析成名字，前端不用额外请求）：

```json
{
  "bySite":   { "3": {...} },
  "byTunnel": { "s1-2": {...} },
  "names": {
    "3":    "群晖 NAS · 照片库",
    "s1-2": "群晖 NAS · SSH"
  }
}
```

名字的拼法是 `设备名 · 服务名` —— 这样即使两个服务同名（不同机器上都有
"Git"）也能分清。解析不到就回落成现在的显示，不会白屏。

前端"各服务流量"按名字显示，穿透的条目仍带「穿透」小标。

## 四、分步实施

| 步 | 内容 | 风险 |
|---|---|---|
| 1 | 数据模型 + 迁移（站点加 deviceId/name，读配置时自动归组） | 低 |
| 2 | 设备增删改接口 | 低 |
| 3 | 反代页改成设备分组 | 中（UI 改动大） |
| 4 | 站点表单加"选设备" | 低 |
| 5 | 流量接口返回 names + 前端显示 | 低 |

第 3 步改动最大，可以单独一个提交，慢慢调。

## 五、取舍与风险

**① 站点一定要挂设备吗？**
建议允许"不挂"（DeviceID = 0），界面上收在「未分组」里。
理由：有人就是想配一个端口转发、后端填个域名而不是 IP，硬要求挂设备会挡路。
但**自动迁移会尽量把它们归进去**，实际很少留在未分组。

**② 两个模块的设备会重名/重复吗？**
会 —— 同一台机器在穿透和反代各有一条记录。这是刻意的（不互相依赖的代价）。
可以后续加一个"从穿透设备导入"的按钮（api 层聚合，扫一次 IP 去重），
但这次先不做，避免范围膨胀。

**③ 站点改名会不会影响转发？**
不会。转发只认 `hosts` 和 `backend`，`Name` 纯粹是显示用。

**④ 老配置迁移出错怎么办？**
迁移逻辑写在读配置那段，且**只在 DeviceID == 0 时触发**（幂等）。
最坏情况是不分组，站点照样能转发 —— 不会把配置改坏。
