# v1.7 方案：反向代理复用局域网扫描 + 统一「设备」概念

状态：待实施 · 2026-10-15 · 目标版本 v1.7

---

## 1. 用户提的问题（原话）

> 反向代理希望也可以一样的扫描设备，原理同 stun 内网穿透。
> 包括添加设备都应该是差不多的，无非一个是 ipv4 穿透一个是公网 ddns。

**对的，这两件事本来就该共用一套。** 现在的差距是历史造成的：

| | STUN（穿透） | 反向代理 |
|---|---|---|
| 添加目标 | 点「扫描」→ 列出局域网机器和端口 → 选一个 → 自动填好 | **纯手填** `192.168.1.20:8080` |
| 设备概念 | 有 Device（`192.168.1.20` 这种），服务挂在设备下 | **没有**，每个站点各写一遍 IP |
| 对外地址怎么来 | 穿透（打洞）动态维护 | DDNS + 反代入口，也要动态维护 |

结果就是：同一台 NAS 在 STUN 那边是「设备+服务」，在反代这边是一串手打的
IP:端口，两边各存一份，改 IP 要改两处。

## 2. 目标形态

**把「设备」抽成两个模块共用的概念**，添加流程也统一：

```
设备（局域网里的一台机器：192.168.1.20）
  ├─ 穿透服务：这台机器的 2573 端口，通过打洞对外暴露
  └─ 反代站点：这台机器的 8080 端口，通过域名 + 反代入口对外暴露
       ↑ 两者都从「扫描结果」里点选，不用手打 IP
```

具体：

1. **共用的局域网扫描**：把 `modules/stun/lan_scan.go` 提到
   `core/lanscan/`（或新建 `modules/lanscan/`），STUN 与 proxy 都调它。
   扫描逻辑本身不用改，只是换个位置让它能被两边用。
2. **反代站点表单加「扫描选择」**：`backend` 字段旁边加一个
   「扫描局域网」按钮，流程与 STUN 完全一致（选网段 → 扫 → 列出机器+开放端口
   → 点一个自动填 host:port，能识别出 http/https 的话顺手勾上 BackendHTTPS）。
3. **可选的设备复用**：新建反代站点时能选「用已有穿透设备」——
   选了就从 device 带出 IP，不用重扫。这是"添加设备都差不多"的落点。
4. **域名从 DDNS 里选**（用户提的）：站点表单的「域名」不再纯手打，
   而是从 DDNS 已配置的域名里下拉选；并能标记这条解析是 **v4 / v6 / 双栈**。
   - 选了双栈的域名 → 站点同时挂 v4 与 v6 入口，卡片上标出来
   - 站点能因此知道自己"对外是靠哪条解析出去的"，不用用户自己对齐两边
5. **站点卡片与 STUN 服务卡片对齐**（用户提的）：启停、编辑、复制、删除、
   「显示在导航主页」都做成同样的交互，只有「怎么出去」那一段不同。

## 2.1 可复用功能清单（用户要求"整理下能复用的"）

按「能直接抽出来共用」到「只借交互」排序：

| 功能 | STUN 现状 | 反代该怎么做 | 复用方式 |
|---|---|---|---|
| 局域网扫描（选网段 → 扫机器与端口） | `pages/Stun.tsx` 内联实现 | 站点表单里同样能扫 | **抽 `components/LanScanModal.tsx`**，两边共用 |
| 服务/站点卡片的一键启停 | `toggleServiceEnabled`（含"这几秒别重复点"的锁） | 站点卡片上加同样的开关 | 抽成 `components/EnableToggle.tsx` |
| 「显示在导航主页」 | `setStunShowOnHome` | 站点也能上主页 | 后端各模块各存一份标记，前端共用按钮 |
| 复制访问地址 | `copy()` + 协议判断（ssh 给 `ssh root@host -p`） | 站点地址复制 | 抽 `lib/copy.ts` |
| 地址面板（多入口、点选哪个） | 服务详情里列地址 | 站点也列（域名 + 入口端口 + v6/v4） | 共用展示组件 |
| 编辑弹窗骨架（分区、校验、保存） | `ServiceModal` | `SiteModal` | 只复用**字段组件与样式常量**，不复用整个弹窗（字段差异大） |
| 扫描结果 → 自动填表单 | `pickScanned()` | 扫描选中后填 `backend` | 接口形状统一，各填各的 |

**明确不复用的**：弹窗主体（字段差太多，硬抽会让两边都变难改）。
复用点放在**字段组件、交互习惯、后端接口形状**这三层。

## 3. 为什么放 core 而不是让 proxy 依赖 stun

`proxy` 依赖 `stun` 会出问题：STUN 启动时要跑网络探测（几秒），
proxy 的监听不该等它。这也是 `home` 模块刻意不写 `dependsOn("stun")` 的
同一个理由（见 `modules/home/component.go` 的注释）。

所以扫描能力要下沉到 **core**（框架层，无业务依赖），两个业务模块各自调：

```
core/lanscan/     ← 扫描实现（从 stun 搬过来，纯网络探测，无状态）
   ↑        ↑
stun      proxy
```

## 4. 实施内容

1. **搬迁**：`modules/stun/lan_scan.go` → `core/lanscan/`，
   导出 `Subnets()` / `Scan(cidr)` / `Host` / `Port` 等同名能力；
   stun 侧改为薄封装（保持 API 与前端不变），跑 `gen_module_imports.py`
2. **反代复用**：`api/proxy_api/` 加两个只读端点
   `GET proxy/lan-subnets`、`GET proxy/lan-scan?cidr=`（复用 core 的实现）

### 域名下拉：怎么拿到 DDNS 的域名（不能直接 import）

反代要列出「DDNS 里配了哪些域名、是 v4/v6/双栈」，但**不能让 `modules/proxy`
去 import `modules/ddns`** —— 那会变成业务模块之间互相依赖，而且 ddns 初始化
要先等 STUN 探测公网 IP（见它 component.go 的说明），代理启动不该被它拖住。

做法：**在 api 层聚合，不在模块层耦合**。

```
api/proxy_api/get_site_options.go   ← 只读地把两边的东西合起来给前端
    ├─ core/lanscan.Subnets()        本地网段
    ├─ ddns.Runtime 的记录快照       ↓ 通过一个只读函数拿，不 import 内部实现
    └─ stun.Runtime 的设备列表
```

`ddns` 侧新增一个只读能力 `ddns.ListDomains() []DomainOption`
（返回 `域名 / 记录类型 / 是否启用`），proxy 的 api 层调它。
这样依赖方向是 **api 层 → 两个模块**，模块之间保持互不认识。

前端拿到的选项长这样：

```json
[
  { "label": "nas.207075.xyz（双栈）", "host": "nas.207075.xyz", "dual": true },
  { "label": "home.1235889.xyz（仅 IPv4）", "host": "home.1235889.xyz", "dual": false }
]
```

站点上存 `hosts: ["nas.207075.xyz"]`（现有字段不动）+ 新增
`preferStack: "dual" | "v4" | "v6"` 记录用户选的栈，卡片上显示出来。

### 前端复用落地

5. **卡片操作对齐**：`components/EnableToggle.tsx`（带"切换中锁定"）、
   `lib/copy.ts`、`components/AddrList.tsx` 抽出来，STUN 与反代两边都用
6. **扫描弹窗共用**：`components/LanScanModal.tsx`，从 `Stun.tsx` 抽出

3. **前端**：`ReverseProxy.tsx` 的 site 表单里加扫描弹窗（组件与 STUN 页
   同款，抽到 `components/LanScanModal.tsx` 共用，避免抄两遍）
4. **设备复用**：站点表单的 backend 旁加「从穿透设备选」下拉

## 5. 验收

- 反代添加站点能点扫描、能从列表里选机器和端口，不用手打 IP
- 站点域名能从 DDNS 已配的域名里下拉选，并显示/记录是 v4、v6 还是双栈
- 站点的启停 / 编辑 / 复制 / 删除 / 上主页，交互与 STUN 服务**完全一致**
- 两边共用同一套组件（扫描弹窗、启停按钮、复制、地址列表），改一处两边都变
- STUN 的扫描行为与 UI 完全不变（搬迁不该被用户感知到）
- **模块之间不新增依赖**：proxy 不 import ddns/stun，一切聚合在 api 层

## 6. 排序

排在通知中心（v1.6）之后。理由：这一版要动 `stun` 的代码位置（搬迁）
+ 反代表单，而通知中心要动 `stun` 的配置读写 —— 都碰 STUN，
同时改出问题会分不清是谁造成的。
