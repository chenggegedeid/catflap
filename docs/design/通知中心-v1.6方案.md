# v1.6 方案：通知中心（Webhook 并入通知）

状态：待实施 · 2026-10-15 · 目标版本 v1.6

---

## 1. 现状：两个东西名字不同，其实是同一件事

| | 现在长什么样 | 问题 |
|---|---|---|
| **Webhook** | `modules/webhook/`：一个通用 HTTP 回调发送器（URL / 方法 / 头 / 体 / 成功判定 / 代理），带「模板」概念 | 配置**挂在每个 STUN 服务的 `webhookconfig` 字段上**，是**服务级**的。新建服务要重填一遍；换个群机器人要改 N 处 |
| **通知** | 散落在各处：证书模块注释里提到"留得下通知用户"、DDNS 有失败状态、STUN 有掉线状态 | **没有统一的发送出口**，各模块各说各话，用户也看不到"这系统到底会通知我什么" |

**核心判断**：Webhook 是「怎么发」，通知是「什么时候发、发什么、发给谁」。
现在只有前者，缺后者，且前者的配置位置放错了（挂在服务上而非全局）。

## 2. 目标形态

一个**通知中心**，三层结构：

```
事件（发生什么）  →  规则（什么事件发给谁）  →  渠道（怎么发出去）
                     ↑ 这是现在缺的一层
```

- **事件**：证书将过期 / 证书续期失败、DDNS 同步失败、穿透服务掉线或重连、
  公网 IP 变化、服务被删除、登录失败次数过多（v1.5 加的限速联动）
- **渠道**：原来的 Webhook 能力原样保留（HTTP 回调），再加几个开箱即用的：
  - 通用 Webhook / 自定义 HTTP（原样）
  - 钉钉、企业微信、飞书群机器人（它们都是 webhook，只是 body 格式固定）
  - Bark / Server 酱 / Telegram（常用推送）
  - 每个渠道有「测试发送」按钮
- **规则**：一条规则 = 选事件 + 选渠道（可多选）+ 可选的条件（如"仅失败时"）

## 3. 数据模型

```go
// 渠道：怎么发
type Channel struct {
    ID      string
    Name    string
    Type    string   // webhook / dingtalk / wecom / feishu / bark / serverchan / telegram
    Enabled bool
    Config  map[string]string  // 按 Type 取不同的键（URL / token / secret …）
}

// 规则：什么事件发到哪些渠道
type Rule struct {
    ID         string
    Name       string
    Events     []string  // 事件类型，见上
    ChannelIDs []string
    OnlyOnFail bool      // 只在失败/异常时发（成功不发），默认 true
    Enabled    bool
}

type Config struct {
    Channels   []Channel
    Rules      []Rule
    // 冷却：同一事件在 N 秒内只发一次，防刷屏
    CooldownSeconds int
}
```

## 4. 迁移：老配置怎么办

**不能丢用户的 webhook 配置**。分两步，且要能回退：

1. **读旧**：启动时扫 `stun` 各服务的 `webhookconfig`，把每个不同的配置
   转成一条 `Channel`（名字取服务名 + " 的 Webhook"），并生成一条规则
   「该服务的掉线/IP 变化 → 这个渠道」
2. **标记来源**：转出来的渠道打上 `MigratedFrom: "stun:<deviceID>:<serviceID>"`，
   原字段**保留不删**（只读不写）
3. **去重**：多个服务配了完全一样的 webhook（同一串 URL/body）→ 合成一个渠道，
   规则里挂多个事件源
4. **回退**：配置文件里 `notify.migrated = false` 时忽略迁移结果，仍走旧字段

`stun` 模块的 `webhookconfig` 字段在 UI 上改为只读展示 + 一句
「已迁移到通知中心，请到那里修改」，避免两处都能改导致不一致。

## 5. 与 v1.5 的衔接

v1.5 先做导航页改版（纯前端），**通知中心排在它之后**，原因：
迁移逻辑要动 STUN 的配置读写，改完必须实机验证穿透仍正常 —— 两件事同时改
出问题会分不清是谁造成的。

## 6. 实施顺序

1. `modules/notify/`：模型 + 渠道发送器（把 webhook/sender.go 的逻辑搬过来，
   按 Type 分发）+ 事件订阅（`bus` 已有，直接订阅 Topic）
2. 迁移逻辑 + 单测（旧配置 → 渠道/规则的转换，含去重与回退）
3. `api/notify_api/` + `routers/` + 前端 `pages/Notify.tsx`（渠道列表 / 规则列表 /
   测试发送 / 发送历史）
4. 各模块接事件：cert（将过期）、ddns（同步失败）、stun（掉线）、auth（登录失败）
5. 旧入口收口：STUN 服务编辑页的 webhook 区改为只读提示；`webhook` 模块
   保留为「发送器实现」，对外不再单独暴露

## 7. 验收

- 老用户升级后：原有 webhook 照常触发（走迁移出来的渠道），配置不丢
- 新用户：不再需要为每个服务重填 webhook；加一条规则就能"证书要过期了发我钉钉"
- 同一事件在冷却窗口内只发一次（防证书检查这种高频事件刷屏）
- 渠道有「测试发送」，能立刻看到通不通，不用等真出事
