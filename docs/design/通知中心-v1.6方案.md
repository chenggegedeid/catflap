# v1.6 方案：通知中心（全局渠道 + 服务引用）

状态：待实施 · 2026-10-15 · 目标版本 v1.6

---

## 0. 一句话：渠道全局定义一次，各服务按名字选用

用户提的关键点，也是这个方案的核心设计：

> 「我在通知里面配置了通知设置（比如邮箱、PushPlus），在 STUN 服务或者其他服务
> 里面能选择全局配置，这样避免每个去配置。」

**对。** 一条推送通道（你的邮箱、你的群机器人、你的 PushPlus token）在整台机器上
只有一份，不应该被复制到每个服务里。所以：

```
通知中心（全局定义）                 各服务（只做引用）
┌────────────────────────┐          ┌──────────────────────────┐
│ 渠道·my-pushplus   ●开 │◀──选用───│ STUN 服务 A 的 webhook   │
│ 渠道·家庭群机器人  ●开 │◀──选用───│ STUN 服务 B 的 webhook   │
│ 渠道·我的邮箱      ●开 │◀──选用───│ 证书将过期提醒           │
└────────────────────────┘          └──────────────────────────┘
       改密码/换 token 只改这里            ↑ 这里只存渠道 ID
```

好处很直接：

- **改一处生效全部**：PushPlus token 过期了，在通知中心改一次，
  所有引用它的服务、规则全都用上新的 —— 不用挨个服务改
- **停用一处生效全部**：渠道上那个 `Enabled` 关掉，所有引用它的地方立刻停发
- **复用而不是复制**：新加服务时下拉选一个已有的，不用重填 URL / 密钥

## 1. 现状：两个东西名字不同，其实是同一件事

| | 现在长什么样 | 问题 |
|---|---|---|
| **Webhook** | `modules/webhook/`：一个通用 HTTP 回调发送器（URL / 方法 / 头 / 体 / 成功判定 / 代理），带「模板」概念 | 配置**整份内联在每个 STUN 服务的 `webhookconfig` 字段上**。同一串 URL 在每个服务里各存一份，改一次要改 N 遍 |
| **通知** | 散落在各处：证书模块注释里提到"留得下通知用户"、DDNS 有失败状态、STUN 有掉线状态 | **没有统一的发送出口**，各模块各说各话，用户也看不到"这系统到底会通知我什么" |

**核心判断**：Webhook 是「怎么发」，通知是「什么时候发、发什么、发给谁」。
现在只有前者，缺后者，且前者的**配置位置放错了**（内联在服务上而非全局）。

## 2. 目标形态

四层，比原来的三层多一层「引用」：

```
通知中心（全局）
  ├─ 渠道：怎么发（URL / token / 密钥）        ← 全局定义，只此一份
  └─ 规则：什么事件发到哪些渠道                  ← 全局事件（证书/DDNS/掉线…）

各服务（局部）
  └─ 引用：这个服务出事时用哪个渠道              ← 只存渠道 ID，不再存密钥
```

- **事件**：证书将过期 / 证书续期失败、DDNS 同步失败、穿透服务掉线或重连、
  公网 IP 变化、服务被删除、登录失败次数过多（v1.5 加的限速联动）
- **渠道**：原来的 Webhook 能力原样保留（HTTP 回调），再加几个开箱即用的：
  - 通用 Webhook / 自定义 HTTP（原样）
  - 钉钉、企业微信、飞书群机器人（它们都是 webhook，只是 body 格式固定）
  - Bark / Server 酱 / PushPlus / 邮箱 / Telegram（常用推送）
  - 每个渠道有「测试发送」按钮
- **规则**：一条规则 = 选事件 + 选渠道（可多选）+ 可选的条件（如"仅失败时"）
- **服务引用**：STUN 服务的编辑页里，webhook 区从「填一堆字段」变成
  「选一个或多个全局渠道」；证书、DDNS 同理

## 3. 数据模型

```go
// 渠道：怎么发。全局唯一一份，谁引用都指向它。
type Channel struct {
    ID      string
    Name    string   // "我的 PushPlus"、"家庭群机器人" —— 下拉里显示的就是它
    Type    string   // webhook / dingtalk / wecom / feishu / bark / serverchan / pushplus / email
    Enabled bool     // 关掉 = 所有引用它的地方立刻停发
    Config  map[string]string  // 按 Type 取不同的键（url / token / secret …）
    // MigratedFrom 老配置迁移来的话，记下出处（便于回退时还原）
    MigratedFrom string
}

// 规则：什么全局事件发到哪些渠道
type Rule struct {
    ID         string
    Name       string
    Events     []string  // 事件类型，见上
    ChannelIDs []string
    OnlyOnFail bool      // 只在失败/异常时发（成功不发），默认 true
    Enabled    bool
}

type Config struct {
    Channels []Channel
    Rules    []Rule
    // Cooldown 同一事件在 N 秒内只发一次，防刷屏
    CooldownSeconds int
}
```

服务侧的引用字段（以 STUN 服务为例）：

```go
// 从 webhook.WebhookConfig（一整份配置）改成：
//   ChannelIDs 只存渠道 ID；[] 空表示这个服务不发通知
ChannelIDs []string `json:"channelIds"`
```

## 4. 迁移：老配置怎么办

**不能丢用户的 webhook 配置**，而且要顺着这次改造把「重复的配置」合起来。

1. **读旧**：扫 `stun` 各服务的 `webhookconfig`，把配置转成全局 `Channel`
2. **去重合并**（这是重点）：多个服务配了**同一串 URL / 同一组字段**的，
   只建**一个**渠道，服务侧都引用它 —— 顺手把用户"复制了 N 份"的历史问题解决掉。
   内容不同的才各建各的，名字取「<服务名> 的通知」
3. **建规则**：为迁移出来的每个渠道生成一条规则「服务掉线 / IP 变化 → 该渠道」，
   让行为与升级前一致
4. **标记来源**：渠道打上 `MigratedFrom: "stun:<deviceID>:<serviceID>"`，
   原 `webhookconfig` 字段**保留不删**（只读），便于回退
5. **回退**：配置里 `legacyWebhookFallback: true` 时忽略迁移结果、仍走旧字段

**为什么原字段要留**：万一迁移逻辑有 bug（比如把某个服务的通知配丢了），
用户可以用一个开关切回旧行为，不至于"升级完通知就没了"。

## 5. 服务侧怎么用（UI）

STUN 服务编辑页的 webhook 区，从「URL / 方法 / 头 / 体」一堆输入框，变成：

```
通知渠道   [✓] 我的 PushPlus        （下拉多选，选项来自通知中心）
           [✓] 家庭群机器人
           [ ] 我的邮箱
           ─────────────────────────
           渠道在「通知」页里统一管理 · 去配置 ↗
```

- 未在通知中心建过任何渠道时，这里显示一行引导 + 「去创建」按钮
- 已停用的渠道在下拉里显示为灰色 `（已停用）`，勾了也不会发，避免"以为发了其实没发"
- 被服务引用的渠道，在通知中心删除时给提示「有 N 个服务正在引用」，
  并给出「改用其它渠道」的选项，不做静默破坏

## 6. 与 v1.5 的衔接

v1.5 先做导航页改版（纯前端），**通知中心排在它之后**，原因：
迁移逻辑要动 STUN 的配置读写，改完必须实机验证穿透仍正常 —— 两件事同时改
出问题会分不清是谁造成的。

## 7. 实施顺序

1. `modules/notify/`：模型 + 渠道发送器（把 webhook/sender.go 的逻辑搬过来，
   按 Type 分发）+ 事件订阅（`bus` 已有，直接订阅 Topic）
2. 迁移逻辑 + 单测（旧配置 → 渠道/规则，含**去重合并**与回退开关）
3. `api/notify_api/` + `routers/` + 前端 `pages/Notify.tsx`（渠道列表 / 规则列表 /
   测试发送 / 发送历史）
4. 各模块接事件：cert（将过期）、ddns（同步失败）、stun（掉线）、auth（登录失败）
5. 服务侧改引用：STUN 服务的 `webhookconfig` → `channelIds`（UI 换成下拉多选）；
   `webhook` 模块保留为「发送器实现」，对外不再单独暴露


## 7. 验收

- 老用户升级后：原有 webhook 照常触发（走迁移出来的渠道），配置不丢
- 新用户：不再需要为每个服务重填 webhook；加一条规则就能"证书要过期了发我钉钉"
- 同一事件在冷却窗口内只发一次（防证书检查这种高频事件刷屏）
- 渠道有「测试发送」，能立刻看到通不通，不用等真出事
