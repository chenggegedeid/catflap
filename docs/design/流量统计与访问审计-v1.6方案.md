# v1.6 方案：流量统计 + 访问审计 + 数据大屏

状态：待实施 · 2026-10-15 · 目标版本 v1.6
优先级：**高**（用户明确要求，且是「管理页第一眼看到的东西」）

---

## 1. 需求（用户原话）

> 网络速率趋势，实时入站速率出站速率，累计入站，累计出站，每天都流量等都要
> 各个服务访问记录以及 IP 统计管理和拉黑，好避免被入侵
> 以后进入管理页面的仪表盘就是各个统计和数据大屏

拆成三件事，**互相有依赖，必须按顺序做**：

1. **流量采集**（基础）—— 没有它，后两件都是空的
2. **访问审计 + IP 管理**（安全）—— 依赖 1 的管道，但统计维度不同
3. **仪表盘大屏**（呈现）—— 依赖 1 和 2 的数据

## 2. 现状盘点

| | 现状 | 差什么 |
|---|---|---|
| 流量统计 | **完全没有** | 从零建 |
| 访问日志 | 有（`modules/proxy/accesslog.go`），但只 `logrus.Infof` 打到日志文件 | 不可查询、不可聚合、重启即丢 |
| IP 封禁 | 有站点级白/黑名单（v1.5 做的），但**静态配置** | 缺「按统计结果动态拉黑」 |
| 仪表盘 | 605 行，展示组件状态/监听/站点概要 | 缺真正的数据可视化 |

## 3. 流量采集怎么采（关键设计）

**在哪采**：反向代理是所有外部流量的必经之路，就在那里采。两个位置：

```
外部请求 → [入口监听] → [路由匹配] → [上游转发] → 内网服务
              ↑ 入站字节                      ↑ 出站字节
```

在 `httputil.ReverseProxy` 的两个方向各包一层计数器：
- **入站**：`r.Body` 外面套一个 counting reader（请求体大小）
- **出站**：`w` 外面套一个 counting writer（响应体大小）

`statusRecorder` 已经是个 ResponseWriter 包装器了，**在它上面加字节计数**就行 ——
不用再套一层，套多了影响性能也容易打掉 Hijack/Flush（accesslog.go 里那段注释
解释过这个坑）。

**不要用 `/proc/net/dev` 读网卡总量**：那是整机所有流量，
分不清「哪些是穿透/反代的服务流量、哪些是系统更新」。用户要的是
**服务维度的流量**，只有从代理层采才对得上。

**采样与聚合**：

```
请求级 → 每条记录累加到 内存计数器（按分钟）
          ↓ 每 60 秒落盘一次
       data/traffic/<YYYY-MM-DD>.jsonl   按天一个文件，每行一分钟的汇总
          ↓ 保留 N 天（默认 90），更早的按天折叠成一条
       data/traffic/summary.json         累计值（累计入站/出站）
```

为什么按分钟而不是按请求落盘：一个被扫描的站点一分钟能有几千条请求，
按请求写盘会把磁盘打满。按分钟聚合后一天最多 1440 行，90 天才 13 万行，
随便查。

**实时速率**怎么来：内存里存「最近 60 秒」的滚动窗口，前端每 2 秒拉一次，
画面上的曲线就是真的实时速率（不是靠磁盘数据拼的）。

## 4. 访问审计 + IP 管理

### 4.1 记录什么

`modules/proxy/accesslog.go` 现在只打日志。改成**同时**写结构化记录：

```go
type AccessRecord struct {
    Time     time.Time
    IP       string
    Method   string
    Host     string
    Path     string
    Status   int
    BytesIn  int64
    BytesOut int64
    Duration time.Duration
    UA       string
    SiteID   uint
}
```

**隐私取舍**：记录里**不存** query string 和请求体。
理由：URL 里可能带 token（`?key=xxx` 一类），而这份记录要长期保留并展示 ——
把凭证写进统计库是很糟的事。需要排障时用「实时日志」那一栏（只打日志不落库）。

### 4.2 存储

```
data/access/<YYYY-MM-DD>.jsonl    当天的明细（超过 N 条就只留聚合）
data/access/ips.json              按 IP 聚合的累计统计
```

按 IP 聚合的那份是给「IP 统计管理」页用的，字段：

```go
type IPStat struct {
    IP          string
    FirstSeen   time.Time
    LastSeen    time.Time
    Requests    int64
    Bytes       int64
    // Status4xx/5xx 计数：扫端口、猜路径的请求大多落在 404
    Errors      int64
    // Paths 访问过的路径去重后取前 N 个（看它在扫什么）
    TopPaths    []string
    // Blocked 是否已拉黑
    Blocked     bool
    BlockReason string
}
```

### 4.3 拉黑怎么生效

**复用 v1.5 做的站点级门禁**，但加一层**全局封禁**（优先于站点规则）：

```
请求进来
  ├─ 全局封禁表里？ → 403
  ├─ 站点白/黑名单？ → 按规则
  └─ 放行
```

- **手动拉黑**：在 IP 统计页点一下，加进全局封禁表，立刻生效（不用重启）
- **一键拉黑可疑 IP**：筛「24 小时内 4xx 超过 N 次」的，批量加入
- **自动拉黑**（可选开关，默认关）：满足条件的 IP 自动封禁一段时间 ——
  **默认关**是因为它容易误伤（比如自己调试时刷出几百个 404 把自己封了）。
  开了之后要有白名单兜底，别把管理员关在外面。

封禁表存 `config/blocklist.json`，带 `ExpiresAt`（临时封禁）与说明。

## 6. 实施顺序（分三个版本点，别一次做完）

| 版本 | 内容 | 为什么这样切 |
|---|---|---|
| **v1.6.0** | 流量采集 + 实时速率 + 累计值 + 仪表盘速率区 | 基础。先让数据流起来，界面先用最简单的数字与曲线 |
| **v1.7.0** | 访问审计落库 + IP 统计页 + 手动/批量拉黑 | 有流量管道之后，审计是同一套采集点的另一种记录 |
| **v1.8.0** | 趋势图 + 服务 Top + 自动拉黑 + 仪表盘完整大屏 | 数据攒够了（几天的历史）图表才有意义 |

**为什么不在一个版本做完**：流量采集本身要跑一段时间才能验证
（有没有内存泄漏、落盘会不会积压、重启后累计值对不对）。
这三件事同时上线，出问题分不清是采集错了还是展示错了。

## 7. 需要注意的坑（先记下来）

1. **性能**：计数要在代理的热路径上做，只做整数加法，不加锁
   （用 atomic）。每请求加锁会明显拖慢高并发场景。
2. **`statusRecorder` 必须继续支持 Hijack / Flush**：WebSocket 和 SSE
   都靠它，加计数时别把这两个接口落了（accesslog.go 里那段注释是踩过的）。
3. **重启后累计值要能接上**：累计入/出站从 `summary.json` 读回，
   不能每次重启从零开始 —— 那"累计"就没意义了。
4. **磁盘写入要有上限**：按分钟聚合是第一步防线；再加「单文件超过
   N MB 就停止写入并记一条告警」，避免被刷爆磁盘。
5. **本机流量别算进去**：自己访问自己的服务（健康检查、探针）要能区分，
   否则统计里永远有一堆噪音。按来源 IP 判断，可配置。
